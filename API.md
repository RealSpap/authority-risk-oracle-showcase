# Data contract, v1

Everything the dashboard shows from the watch is a file rewritten by the `Watch` GitHub Action at each run (scheduled every 6 hours, `17 */6 * * *` UTC; about 2 runs a day since 4 Nov 2026, 2 to 4 from 31 Oct to 6 Nov), committed to the `watch-data` branch of this
repository (the root of the branch is the folder that is called `watch/` in the scripts and in this document) and served raw from
`https://raw.githubusercontent.com/RealSpap/authority-risk-oracle-showcase/watch-data/latest.json` (and in the same way for every other file of the branch). `main` holds the code and the documents written by hand (this one, the README and
the schemas, copied into the branch at every run), so its history is the history of the work. Before the move the same files were committed to `main` under `watch/`; those commits stay,
and the old links answer with a short notice that points here. `status.json` carries `data_location`, the base URL under which every file is served, so a page or a monitor does not need a constant of its own (the notice left on `main` carries it too). No key, no rate limit beyond GitHub's. The on-chain source of truth stays the oracle contracts (`getScore(address)`): these files are a convenience read of them.

**What the checks do not prove (written down on 2026-10-11 after a security review).** (1) The signature is checked with the public key written *inside* `signature.json`: a forged manifest signed with a random key still says "valid". It proves the files match what that key signed, not who holds the key; the maintainer's public key is `11baca3ef6a69de4901c185f6cbbd3f93318fbb74f9961a8d39aead841adf409`, pinned in the dashboard page of the site (`ARO_PUBKEY`; the file `dashboard/index.html` of this repository has no signature check) and written here: compare it with the `public_key` of `signature.json`, and treat a signature made by any other key as invalid. Before 2026-10-11 21:18 UTC the runs were unsigned (`signed: false`), and a run that cannot read the secret says so. (2) `verify_chain.py` checks that every line commits to the previous one; it cannot see that the *end* of the log was cut off. The head of the chain is pinned in the signed manifest (`events_chain_head`), so compare that value, not only "chain intact". (3) An alarm is a line of `events.jsonl` and an issue in the maintainer's private repository, and only when the `ISSUES_TOKEN` secret is set: without it the run prints "alarm raised but no ISSUES_TOKEN" and nobody is told. An oracle that stops answering raises one alarm, then stays silent while it stays unreadable: read `status.json` for the current state. 

Auditing all of this from outside, in one command and with the standard library only: `python3 scripts/audit_public.py` fetches the published files, checks the event-log chain, the signed manifest and its signature (pynacl), the schemas, the methodology registry, and re-reads a random sample of scores from the oracle contracts over public RPCs; `--watch watch` audits a local checkout, `--sample N` sets the sample, `--ref <commit>` audits a past run as it was committed (its signed manifest, chain and schemas), since every run commits its manifest. Exit 0 means every check passed.

Reproducing a read: every share page (`/oracle/p/<chain>-<address>.html` and its `.json` twin, field `reproduce`) carries the exact `eth_call` (oracle, calldata, block of the build) that re-reads the score from the public RPC; the 6th word of the answer is the composite. One RPC (Hyperliquid testnet) answers for the latest block whatever block is asked, measured on 2026-10-10 with the same `trackedTargetsCount()` at block 1 and at latest: those pages say so and pin `latest` (`block_honoured: false`).

What changed since a moment: the dashboard takes `#since=<UTC time>` (for instance `#chain=all&since=2026-10-10T06:00Z`) and lists every move and alarm of `events.jsonl` recorded after it; the button under the hero copies such a link marked at the current time.

Subscribing: every run commits to `watch/`, so a GitHub webhook on this repository (event `push`, filter on paths under `watch/`) tells your service within seconds; the Atom feeds (`feed.xml`, `alerts.xml`) and the calendar (`pending_ops.ics`) need no account; the dashboard's "notify me" polls `latest.json` every 10 minutes in the browser.

**Signed webhook for a machine.** If the workflow has the secrets `ALERT_WEBHOOK_URL` (https only) and `ALERT_WEBHOOK_SECRET`, every run that raises new alerts POSTs `{"event":"alerts","version":1,"sent_utc","alerts":[{rule,severity,chain,target,title,score,delta,tvl_usd,first_seen}],"page"}` (ten at most). Headers: `X-ARO-Timestamp` (unix seconds) and `X-ARO-Signature: sha256=<hex>`, the HMAC-SHA256 of `<timestamp>.<raw body>` with your secret. Check the signature on the raw bytes with a constant-time comparison and refuse a timestamp more than five minutes old. **`signature.json` alone does not show that a run is fresh.** When signing is refused, the Watch run goes on and publishes its files with the `signature.json` of the run before (`SECURITY.md`). A consumer who reads only `signature.json` then sees `signed: true` and a valid signature for the older manifest. To know that the signature belongs to the files being read, check that the sha256 of the `latest.json` you read is the one listed for `latest.json` in `manifest.files` of a valid signature (a signature from an earlier run lists the hash of an earlier file), or run `python3 scripts/audit_public.py`, which exits with code 4 when the signature is from an earlier run than `latest.json` (it compares the `run_utc` of `signature.json`, which is written next to the manifest and is not signed). `status.json` says `signature_status: stale` in that case. Since 30 October 2026 the three files carry `run_id` (the Actions run and attempt of the passage; in `signature.json` it sits next to the manifest and is not signed): `audit_public.py` exits 4 when the `run_id` of `signature.json` and that of `latest.json` differ, and the Watch workflow runs `scripts/check_run_id.py` after signing.

**Files that are published but are not in the signed manifest.** The manifest lists every published `*.json`, `*.jsonl`, `*.xml`, `*.md`, `*.ics` and `*.csv` file under `watch/` except, wherever they are under `watch/`: `signature.json` itself; `alarm.md`, `alerts_high.md`, `alarm_state.json`, `methodology.md` and any `who_controls.json`; `status.json`, `integrity.json` (`badge/integrity.json`) and `catalog.json`, summaries written after the signature from signed sources; everything under `og/` (the share images and `og/index.json`); the job logs (`*.txt`, `*.log`). `metrics.prom` is not listed either, because its extension is not one the manifest takes. A symbolic link, a folder that is a link and a `private` folder do not enter the manifest, and names that start with a dot (a `.gitignore` at the root of the branch, for example) are not in it either. `status.json`, `integrity.json` and `catalog.json` can be recomputed from the signed files; the alarm files are an internal state. None of the files in this list is signed.

**The dashboard is a fixed interface reading live data.** The page you load is the interface of one commit; the numbers it shows are read when you open it, from the chains and, on the page served online, from these files. An old interface can therefore show current data, and the interface served on the site may differ from `dashboard/index.html` in this repository.

**The webhook and the other alert channels: what is guaranteed.** In one run, each channel is tried once: there is no retry inside a run. Of the alerts that are new in a run, the message carries the first ten; the others are not sent in that run and are tried again at the next run, 6 hours later. Since 30 October 2026 the delivery state is kept per alert AND per channel (`delivered` in `alerts.json`): an alert is marked as delivered (`notified: true`) only when every channel it needs has carried it, a channel that failed is tried again at the next run, while the alert is still active, without sending the alert again to the channels that already carried it, and the message title says how many alerts the channel is owed while the text lists at most ten. (Before that change an alert was marked as delivered when at least one channel accepted it.) Four more facts: only alerts of medium severity and above are sent (`notify.min_severity` of `rules.json`); the Discord text is cut at 1900 characters and the Telegram text, when longer than 4000 characters, at 3900, and an alert that falls in the cut part is still marked as delivered; an alert is also marked as delivered when no channel is configured, so an alert raised while nobody was set up to receive it is not sent later; and "new" in a run includes the alerts that an earlier run could not deliver. Delivery is not guaranteed, and a receiver that must not miss an alert should also read `alerts.json` or `status.json`, which carry the current state. (Checked in `scripts/evaluate_rules.py`, as of 30 October 2026.)

**The Atom feeds are a sliding window, not a history.** `feed.xml` carries the last 60 events; `alerts.xml` the last 60 entries of the alert history; the feed of one contract (`feed/<oracle-slug>/<address>.xml`) and the feed of one protocol (`feed/protocol/<slug>.xml`) carry the 50 newest entries. An older entry leaves the feed. Older moves and alarms stay in `events.jsonl` of the `watch-data` branch, which is append-only and hash-chained; older alerts stay in the `history` of `alerts.json`, which keeps the 500 most recent; `history.jsonl` holds one line of counters per run.

**A Safe nonce says that the Safe acted, not what it did.** `safe_activity.json` compares the `nonce()` of a Safe from one run to the next: a higher nonce means transactions were executed, and says nothing about their content. The file is not linked to the decoded operations in `pending_ops.json`. To see what a Safe did, read its executed transactions.

**A secondary role with no getter is not covered, which is not the same as no role.** `side_roles.json` lists the contracts that answered one of seven getters. A contract that answers none of them has no record and is listed in `no_getter_recognised`; that says nothing about whether it has such a role (see `docs/LIMITS.md`).

## Added on 31 October 2026: the state a run starts from

Every run extends files of the previous run (`events.jsonl`, `history.jsonl`, the history of `alerts.json`) and signs the folder again. Before it reads anything, `scripts/check_previous_state.py` checks the state it starts from against the `signature.json` the previous run wrote. A change pushed to `watch-data` between two runs, by someone who does not hold the key, would otherwise be signed by the next run.

| Case | What the run does |
|---|---|
| the signature of the previous manifest verifies (against the published key in the canonical repository), every file of the manifest has its hash, no published file was added, the event log ends at the signed head | continues |
| any of those fails, a file is gone, `signature.json` cannot be read or is by another key | **refuses**: nothing is read, nothing is recorded on `watch-data`, the job is red, and an alarm issue is opened every time (the alarm gate cannot make it quiet). A refusal that stands opens an issue at every run: the Watch is stopped until someone looks |
| `signature.json` is gone, in a repository that signs, whatever `events.jsonl` looks like (absent, empty, unreadable, cut) | **refuses**: a missing state is not an empty state, and the run that followed would sign the emptied state with the real key. Only a repository with no signing key reads "no signature and no event log" as a first run |
| the state is older than the last successful run of the workflow (an older signed state put back on the branch) | **refuses**, when the workflow could read the list of runs (the step "The last successful run of this workflow"). The date of the state is the `run_utc` of `latest.json`, a signed file; the `run_utc` written next to the manifest in `signature.json` is not signed and is not used. If the list cannot be read, the check is skipped and the run says so with a warning |
| PyNaCl is not installed (script exit 3) | does not continue and says the signature was **not checked**; this is not a finding about the state (`pip install -r scripts/requirements.txt`) |
| the signature of the run itself failed (key present, PyNaCl missing, a file the audit would refuse) | the job stops at the signing step and **does not record**: the next run starts from the last signed state. The daily report that cannot be signed again is not recorded either |

The first signed run of a repository that signs is started by hand (Actions, Run workflow) with the repository variable `WATCH_BOOTSTRAP` set to `1`; it accepts a previous state that has no signature, never a signature that does not verify, a key that is not pinned or a file that differs. Scheduled runs ignore the variable. Every run that sees the variable, used or ignored or left on although the state is signed, prints an `ALARM` line and opens an issue: remove the variable after the first signed run.

What this does not cover: the files that are not in the signed manifest (`alarm_state.json`, `alarm.md`, `metrics.prom`, `catalog.json`, `og/`, `private/`, hidden files) can be changed on the branch without a refusal; the documents copied from `main` at each run are not compared; a fork with no pinned key accepts a state signed again by any valid key; and an older state put back is seen only through GitHub's list of runs, not through anything in `watch-data` itself.
